# レビュー手順書（既存UIを診断・改善する）

コードやスクショを渡されたら、いきなり書き換えず**まず診断→優先度つき提案**の順で。
勝手に大改造しない。既存の意図が読めない箇所は確認する。

## 診断の進め方

### 1. 全体印象（薄目テスト）
まず細部を見ずに全体を見る。「一目で主役がわかるか」「どこかで見たテンプレか」
「このプロダクトらしさがあるか」を言語化する。

### 2. テンプレ臭スキャン
`anti-template-tells.md` の"におい"リストと照合し、当てはまるものを**具体的に**挙げる。
「なんか安っぽい」ではなく「`indigo-500` がデフォルトのまま」「全カードに `shadow-md`」
「見出しと本文が同サイズ」のようにコード/箇所を特定する。

### 3. 意図の欠落チェック
色・サイズ・余白・角丸で「なぜこの値か説明できないもの」を洗い出す。
中途半端な余白（13px等）、バラバラの角丸、根拠のない配色は意図の欠落サイン。

### 4. らしさの欠落チェック
「これを競合や無関係なプロダクトに貼っても成立するか？」成立してしまうなら無個性。
記憶に残る署名的要素が1つでもあるか。

## 提案の出し方

- **優先度順に、効果の大きいものから。** 一般に効きやすい順序:
  1. 配色の再定義（主役色・色付きニュートラル・脱デフォルト紫）
  2. タイポの階層化（見出し/本文の差、行間、measure）
  3. 余白の階層化（均一 → 意味に応じた強弱）
  4. 状態・ディテール（hover/focus、空・ローディング）
  5. 署名的ディテールを1つ足す（らしさ）
- 各提案に **なぜ良くなるか** を一言添える（例:「純黒→off-blackで目が楽になり上品に」）。
- 破壊的な全面作り直しは提案しない。既存を活かした最小の高効果変更を優先。
- コードで示すときは、変更対象の箇所を特定し diff 的に（どこをどう変えるか）示す。

## レビュー出力テンプレ

```
## 総評
（薄目テストの印象。良い点も1つは挙げる）

## 気になった点（テンプレ臭・意図/らしさの欠落）
1. [箇所] — [何が問題か] — [なぜ安く見えるか]
2. ...

## 改善提案（優先度順）
1. [変更内容] → [なぜ良くなるか]
   （必要ならコード例）
2. ...
```

良い点も必ず拾う。全否定はモチベを削ぐし、活かすべき既存の意図を潰しかねない。
