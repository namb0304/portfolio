### 1.2 監査の結論（5点）

**(1) 最大の資産がサイト上に存在せず、しかも積極的に誤解を生んでいる。**
Hirolia は `config/index.ts:236-247` に 2 件だけ存在するが、記述は「2025年11月 始動」と「2025年12月 プロトタイプを開発しました。賞は取れませんでした」で止まっている。実店舗5店舗・有料契約・本番運用という事実がないばかりか、**サイトを読んだ人は「学内ハッカソンで作ったプロトタイプ」と結論する。** 不在より悪い。

**(2) コンテンツの最終更新が2025年12月。9ヶ月の空白が可視化されている。**
`config/index.ts` の timeline 最終項目が 2025年12月。一方 `components/Footer.tsx:5` は `new Date().getFullYear()` で 2026 と表示される。**「2026年のサイトなのに2025年で更新が止まっている」という齟齬が、フッターによって毎回証明される。**

**(3) データモデルが「作品カタログ」であり、経験を表現できない。**
`Project` 型は `title / description / category / tags / image / url / github` のみ（`config/index.ts:91-165`、`types/index.ts:9-17`）。**担当範囲・期間・チーム規模・課題・意思決定・結果を入れる場所が型レベルで存在しない。** `description` は実運用上 1〜2文（最長でも `config/index.ts:121` の約80字）。この器に Hirolia を入れると、必ず「モバイルオーダーを作りました」の1行になる。ここが本監査の核心。

**(4) 情報アーキテクチャが「技術を触っている学生」像を構造的に生産している。**
最初の1画面は背景画像のみで情報ゼロ（`components/ProfileHeader.tsx:25-33`）。2セクション目が Skills で、**Projects より先に「触った技術14個のアイコン一覧」が来る**（`app/page.tsx:17-25`）。本番運用の PostgreSQL と、プロジェクトにも timeline にも一度も登場しない Flutter（`config/index.ts:78`）が同じ重みで並ぶ。これは本人が最も避けたい像そのもの。

**(5) 自己紹介の文言が、現在の自己認識と直接矛盾している。**
`config/index.ts:29` の bio が「UI/UXを中心に、フロントエンドを軸としつつ」「**フロントエンジニアを目指しています**」と明示。現在の「フロント固定で見せたくない」という方針と真逆の宣言がサイト上にある。

### 4.3 ギャップの原因は3層ある

**第1層：内容（文言が古い）**
Hirolia / STORES が無い、bio がフロント志望のまま。→ **文言更新で解決する。** 設計書が主に扱っているのはここ。

### 6.2 個別の根拠

**Hirolia（`config/index.ts:236-247`）**

現行の2行は、意図と逆方向に働いている：
- 「経営学部の友人に…実装を**依頼され**」→ 受け身の表現。課題を自分で捉えた人には読めない。
- 「賞は取れませんでしたが**システムの大枠を完成させることができました**」→ **ここで話が終わっているため、読者は「大枠で止まった」と理解する。**

現在の実態（顧客画面・管理画面・API・DB設計・Render本番運用・エラー監視・外形監視・GitHub Actions CI・DBバックアップ・本番障害対応・店舗別設定・一部マルチテナント・5店舗継続運用）は、**現行のProject型では1フィールドも表現できない。** これが §4.3 第3層の最も具体的な証拠。

重要なのは「Webアプリを作った」ことではなく「開発環境で見えなかった問題に現場で直面した」ことなので、**Project Card 1枚という前提は成立しない。** 必要なのは「課題 → 判断 → 起きたこと → 直したこと」という時間軸を持つ器。

**STORES（サイト上に不在）**

「有名企業のインターン参加」として置くと、Activities の受賞3件と同じ「肩書の列挙」になり、本人が避けたい見せ方に合流する。一方、失敗と学び（実装が始まると『誰の何を変える機能か』を判断基準として保持できなくなった）は、**「プロダクト思考を伸ばしている途中」という自己申告に対する唯一の具体的な裏付け**になる。

→ 情報量は中〜大だが、**置く場所は Projects でも Activities でもない可能性が高い。** IAの論点（§12-2）。

**Thank x Chain（`config/index.ts:119-127`）**

現行で唯一「改善のプロセス」が書かれている項目（「コンセプトの見直しからリファクタリング・UI/UXの改善」）。**既存資産として最も価値が高い。** ただし現状は1文。Thanks（同 `111-118`）と合わせて「一度作ったものを作り直した」という一続きの話にできる。なお両者の `github` は同一リポジトリ（`RSS_Hackathon_namelesz.git`）で、**カードを2枚並べる根拠が薄い。**

**Portfolio 自身（`config/index.ts:92-100`）**

- カルーセルの**1枚目**を占有している = 最初に見えるプロジェクトが「今見ているこのサイト」。
- `url: "#"` → `ProjectCard.tsx:13` の判定で `primaryUrl = "#"` となり、**カード全体が `<a href="#" target="_blank">` になる。クリックすると同じページが新しいタブで開く。**（実害・バグ）
- サイトそのものが実物として存在する以上、カードは冗長。

**「なし」センチネル（`config/index.ts:135, 152, 161`）**

`url: "なし"` の2件が **「デプロイ準備中...」** と表示される（`ProjectCard.tsx:53-55`, `ProjectsCarousel.tsx:69-71`）。実際には「デプロイする予定がない学習用プロジェクト」であり、**「未完成のまま放置している」という誤ったシグナル**を出している。「最後まで使える状態に持っていく」という強みと真逆。

## 14. 最終判定：今の設計書のまま実装を開始してはいけない理由があるか

# **Yes**

### 理由1：設計書の前提事実に誤りと陳腐化があり、内容更新フェーズ（Step 3）が起動できない

設計書 §9-6 は卒業年度を「27卒で相違ないか」としているが、**正しくは2028卒**（2024年入学・現3年）。Hero に「◯◯卒」を明記する設計になっているため、**この誤りは最も目立つ場所に出る。**

さらに §2.2 の実績サマリ「実店舗導入3店舗」は現在5店舗、§3.5 で追加予定の Activities 3件は7月時点の到達点で止まっており、**STORES インターン（2026年8月）は設計書に存在しない。**

Step 3（`config/index.ts` の内容更新）は設計書上「質問回答」依存とされ、§9 の8項目が**7月から一つも解決していない**。Step 4〜8 はすべて Step 3 に依存する。**内容が確定しない状態で見た目から作ると、確定後にレイアウトが破綻する**（設計書 §7 自身が「実データ耐性」を確認観点に挙げているとおり）。

---

### 理由2：決定事項 B / C / D が、現在の目的から見て再検討対象であり、設計の骨格が固まっていない

- **決定事項 B（主役色 濃紺）**：設計書自身が「配色だけでは差別化がほとんど効かない」と認めており、差別化に寄与しない色を確定させている。
- **決定事項 C（トグル5系統を全維持）**：設計書自身が「切替の存在自体が**設計判断の不在**に見える」と診断しながら、「資産の破棄になる」を理由に全維持を決めている。**「せっかく実装したから残す」の構造そのもの。** しかも残す対象のアクティブ状態は **コントラスト 2.37:1 で AA 不適合**（§7.5）であり、「アクセシビリティ配慮の証拠」という維持理由自体が成り立っていない。
- **決定事項 D（GitHub Activity 内製化）**：本人が「情報設計上の優先度は低くてよい」と明言している要素に、実装コスト上位（サーバー実装・PAT運用・レート制限対応）を割り当てている。

加えて、**§2.2 の肩書「Frontend-focused Product Engineer」は現在の自己認識と真逆**であり、§1.6（階段タイムラインの主役化）は §5-判断1 で「リニューアルの成否そのもの」と位置づけられているが、本監査では RETHINK と判定した（横スクロール強制・SP での384pxずれ・傾きが内容と無関係）。

**骨格に相当する判断のうち、色・トグル・GitHub・肩書・署名的ディテールの5つが同時に動く。** この状態で Step 1（トークン定義）から着手しても、Step 4〜7 でやり直しになる。

---

### 理由3：最大の課題（一気通貫の経験を入れる器がない）に、設計書がまだ答えていない

現行の `Project` 型は `title / description / category / tags / image / url / github` のみ。設計書 §3.4 の手当ては **「role / period / teamSize の3フィールド追加」**で止まっている。

これは属性情報であって、**Hirolia の本質（店舗Wi-Fi・Service Worker cache・端末差・複雑な実メニュー・本番障害・監視・継続運用という、開発環境では見えなかった問題に現場で直面したこと）は `role: string` には入らない。** STORES の本質（「誰の何を変える機能か」を判断基準として保持できなくなった、という思考の失敗と回復）も同様。

**器を決めずに実装すると、Hirolia は結局「モバイルオーダーSaaSを開発しました（役割：フルスタック／5人）」という1枚のカードになる。** それは現在のサイトと本質的に同じであり、伝えたい人物像（課題理解 → 要件定義 → 設計 → 実装 → 導入 → 運用 → 改善）との距離は縮まらない。

**この論点（§12 の 1 と 2）を先に決めることが、次フェーズの唯一の入口。**
