## 1. デザイン方針（土台）

実装前にこれを固める。コードを書きながら色や余白をその場で決めるのが、テンプレ感の最大の原因のため。

### 1.1 キャラクター1語 — **実直**

飾らない。誇張しない。書いてあることが全部本当だと分かる佇まい。

**なぜこの1語か**: 新しい名乗りの核が「動くもの ≠ 使われ続けるもの」である以上、**装飾で盛ったサイトはその主張自体と矛盾する**。抑制されていること自体が主張の裏付けになる。以降のすべての判断（色を足すか、影を落とすか、アニメーションを増やすか）は、この語に照らして決める。

判断に迷ったら: 「これは実直か？」→ No なら入れない。

### 1.2 主役色 — **濃紺 #1e3a5f**（ダーク基調を継続）

**決定**: 基調はダーク継続（決定事項A）、主役色は濃紺（決定事項B）。

**なぜ濃紺か**: 業務システムを扱う実直さを、落ち着いた紺で表す。信頼・堅実の色相であり、「現場で使われ続けるプロダクト」という名乗りと矛盾しない。

#### ⚠️ この選択に伴う制約と、その対処

**濃紺 × ダーク基調は、現行の「ダーク + cyan/blue」とほぼ同じ座標にある。** つまり**配色だけでは差別化がほとんど効かない**。加えて #1e3a5f は暗背景上で輝度が足りず、CTA の塗りには使えない（実測 約3.5:1 = 本文コントラスト AA 未達）。明るくすれば使えるが、それは結局いまの青に戻る。

したがって以下3点で差別化を担保する。**色ではなくタイポ・余白・抑制で差をつける方針に切り替える**（これは「実直」という1語にはむしろ忠実）。

1. **主要CTAは濃紺の塗りにせず、白系反転ボタンにする。** 暗背景で最も強く、かつ最も抑制的。
2. **ニュートラル全階調に濃紺の色相を通す。** Tailwind 既定の cool gray をやめる。画面全体の統一感はここで出す。
3. **テンプレ臭の本体は「青いこと」ではなく「グラデ文字 × 全中央揃え × 均一余白」。** そこは配色選択と無関係に潰せる（§1.1 / §1.3 / §1.4）。

#### トークン定義

```css
@theme {
  /* ニュートラル: 純グレーをやめ、全階調に濃紺の色相を通す */
  --color-bg:         #0d1219;  /* 濃紺寄り off-black。#000 は使わない */
  --color-surface:    #141c26;  /* カード面 */
  --color-border:     #23303f;
  --color-ink:        #e6ecf2;  /* off-white。#fff は使わない */
  --color-ink-mute:   #8d9cad;  /* surface上で 約6.1:1 = AA 適合 */

  /* 主役色 */
  --color-brand-deep: #1e3a5f;  /* 選択された濃紺そのもの。面・境界・区切りに */
  --color-brand:      #3f6d9e;  /* 暗背景用に持ち上げた版。アクティブ状態・大きい文字 */
                                /* bg上 約3.5:1 → 小さい本文には使わない */
  --color-brand-text: #7aa8d4;  /* 小さい文字に主役色が要るときだけ。bg上 約7.6:1 */
  --color-brand-weak: #18242f;  /* 選択状態の背景 */

  /* 主要CTA: 濃紺ではなく白系反転（上記の理由により） */
  --color-cta:        #e6ecf2;  /* bg上 約15.9:1 */
  --color-cta-ink:    #0d1219;
}
```

**主役色の用途を 2 つに限定する**（現行は 9 用途に拡散）:

| 使う | 使わない |
|---|---|
| アクティブ状態（選択中のトグル・フィルタ） | タグの文字色 |
| タイムラインの「実運用到達」ノード（§1.6） | スキルアイコン |
| | タイムラインの全ドット |
| | 見出しのグラデーション（**全廃**） |
| | 主要CTA（→ 白系反転を使う） |

→ 現行は cyan が 9 用途に散っていたため「押せる場所」を意味できていなかった。用途を絞ることで、薄目で見たときに CTA とアクティブ状態だけが立つ。

### 1.3 タイポグラフィ

**書体: IBM Plex Sans JP（見出し・本文）+ IBM Plex Mono（日付・数値・タグ）**

- **なぜ**: 「実直」に対応する硬質でエンジニアリング寄りの表情。和欧のファミリーが揃っており、混植で崩れない。
- **現行の問題**: Inter は latin subset のみで**日本語フォント指定が無く、OS依存**（Mac=ヒラギノ / Win=游ゴシック）。見る人の環境で印象が変わるポートフォリオになっている。
- Mono を日付・タグ・数値に使うことで、**署名的ディテールの一部**にする（§1.6）。

**タイプスケール（比率 1.25 = Major Third）**

```
12 · 14 · 16(本文) · 20 · 25 · 31 · 39 · 49 px
```

| 用途 | サイズ | ウェイト | 行間 | 字間 |
|---|---|---|---|---|
| ヒーロー見出し | 39 / 49 | 700 | 1.15 | -0.02em |
| セクション見出し | 25 / 31 | 700 | 1.2 | -0.02em |
| カード見出し | 20 | 600 | 1.3 | -0.01em |
| 本文 | 16 | 400 | **1.75**（和文のため広め） | 0 |
| 補助・キャプション | 14 | 400 | 1.6 | 0 |
| 日付・タグ（Mono） | 12 / 14 | 500 | 1.4 | 0 |

- 見出しと本文で**最低1.5倍以上の差**をつける（現行は実質1段階しかない）。
- **measure 制限**: 和文は全角 34〜38 字。`max-w-[36rem]` 前後。現行の `max-w-3xl`(768px) は約42字で超過。

### 1.4 スペーシング

**4px ベースのスケール1本で全体を縛る**:

```
4 · 8 · 12 · 16 · 24 · 32 · 48 · 64 · 96
```

**入れ子の大小関係を必ず守る**（現行はここが壊れている）:

```
セクション間  96px (SP: 64px)
  > セクション内グループ間  32-48px
    > カード間  24px
      > カード内 padding  16-20px
```

現行は セクション padding `p-8`(32) ≒ カード間 `gap-8`(32) ≒ カード内 `p-6`(24) でほぼ同格。「詰まって見える」原因はここ。

### 1.5 コンポーネントの質感

- **角丸は1基準**: カード `10px` / 内側要素（タグ・入力・ボタン）`6px` / 円形は例外（アバター・ドット）。
  - 現行は `rounded-lg` / `rounded-xl` / `rounded` / `rounded-full` が混在し、**同じプロジェクトカードなのにグリッドは lg、カルーセルは xl**。
- **影は原則廃止**。区切りは `border 1px` **か** 背景差の**どちらか一方**（全部盛りしない）。
  - 影を許可するのは「浮いている物理的理由」があるものだけ = モーダル / カルーセルの選択中カード。
  - 現行は並列カード全部に影があり、しかも `shadow-lg` / `xl` / `2xl` が理由なく混在。
- **状態を必ず用意**: hover / focus-visible / active / disabled。
  - `focus-visible` を消さない。現行は `focus:` （マウスクリックでもリングが出る）なので `focus-visible:` に寄せる。
  - トランジションは 120〜180ms。長いともっさりする。

### 1.6 署名的ディテール（らしさ）

**既存の「階段状タイムライン」を主役に昇格させる。**

現行 `Timeline.tsx` の横型表示は、項目が右肩上がりに積み上がるレイアウトになっている（`marginBottom: slopeValue`）。**これはこのサイトで唯一「記憶に残る要素」**であり、しかも「成長の軌跡」という内容と形式が一致している。問題は、トグルの裏に隠れていてデフォルトが `vertical` であること。

**強化案**:

1. 横型をデフォルト表示にする。
2. 日付を **IBM Plex Mono** にする（§1.3）。
3. **「Hirolia 実店舗導入（2026年4月）」以降のノードだけを主役色で塗る。** それ以前はニュートラル。
   → 「軌跡が右肩上がりで、**実運用に到達した地点が色で分かる**」という一枚の絵になる。これが §0 の一行を視覚化する。

これが「別プロダクトに貼っても成立してしまう」状態からの脱出点になる。

## 5. 重要な設計判断

### 判断1: ライト基調に転換するか、ダークを磨くか

→ **決定: ダーク継続（現行を磨く）**

変更範囲が小さくリスクが低い。既存資産を活かせる。

**トレードオフとして受け入れたこと**: ダークである限り「開発者ポートフォリオ感」は残り、しかも主役色に濃紺を選んだため**配色による差別化はほぼ効かない**（§1.2 参照）。この判断の帰結として、差別化の負担はタイポグラフィ・余白階層・主役色の抑制・署名的ディテールに全面的に移る。**つまり §1.3 / §1.4 / §1.6 は「あれば良いもの」ではなく、このリニューアルの成否そのものになる。**

### 判断2: 表示トグル（切替UI）をどうするか

現行は Projects に カルーセル/グリッド、Timeline に 縦/横 + 昇順/降順 + タグフィルタ の**計5系統の状態**を訪問者に委ねている。

- **問題**: 実装力のアピールにはなるが、採用担当は「操作しに来ている」のではなく「10秒で把握しに来ている」。切替の存在自体が「どう見せたいか決めきれなかった」という**設計判断の不在**に見える。
- **一方**: トグルの実装（`aria-pressed` 等）はアクセシビリティ配慮の証拠でもあり、全廃は資産の破棄になる。

→ **決定: B — すべて残し、デフォルト値だけ変更する。トグルの削除は行わない。**

- Timeline: 縦/横トグルを維持し、**デフォルトを `horizontal` に変更**（署名的ディテールを既定で見せる）
- Projects: カルーセル/グリッドのトグルを維持。デフォルトは現行どおり `carousel`
- ソート・タグフィルタも維持

**この決定の帰結**: 訪問者に委ねる状態は 5 系統のまま。「10秒で把握させる」導線は、トグルを減らすのではなく**ヒーロー（§2.2）で担保する**。ヒーローに実績サマリと3ボタンを置くことで、下までスクロールしなくても人物像が伝わる状態を作る。ヒーローの設計品質がより重要になる。

### 判断3: GitHub Activity の外部依存

現行は `ghchart.rshah.org` と `github-readme-stats.vercel.app`（どちらも無料の個人運営）に依存。実際に落ちる（コミットログの「おそらくサーバー状態によりけり」がそれ）。**採用担当が開いた瞬間に画像3枚が壊れているリスク**がある。

→ **決定: B — GitHub GraphQL API + Next.js ISR で自前実装する。**

外部サービス障害の影響を受けなくなり、実装自体が技術アピールになる（運用を重視するという軸とも一致する）。

**実装方針**:

- GitHub GraphQL API の `contributionsCollection.contributionCalendar` から日別コントリビューションを取得
- Server Component + `revalidate: 3600`（ISR）でビルド時・定期再生成。クライアントにトークンを渡さない
- PAT（`read:user` スコープのみ）を `GITHUB_TOKEN` として環境変数管理。`.env.local` と Vercel の両方に設定が必要
- **貢献グラフは SVG を自前描画**（外部画像に依存しない）。色は §1.2 のトークンから生成した5段階
- 言語構成は `repositories(ownerAffiliations: OWNER)` の `languages` を集計
- **失敗時のフォールバックを必ず用意する**（API が落ちる / レート制限 / トークン失効）。空状態として「GitHubで見る」リンクを表示し、**セクションが壊れて見えないこと**を保証する
- `next.config.ts` の `remotePatterns`（ghchart / github-readme-stats）は不要になるため削除

**注意**: これは他ステップと独立性が高く、かつ唯一サーバーサイドの実装を含む。**Step 9 として最後に分離**し、他の見た目の変更を先に完了させる。

### 判断4: デザイントークンの置き場所

Tailwind v4 では `tailwind.config.ts` は**自動で読まれない**（`globals.css` に `@config` が無いため）。現行の `font-dancing-script` と `scrollbar-*` はこの理由で**完全に死んでいる**。

→ `globals.css` の `@theme` にトークンを集約する。設定ファイルの二重管理を避けられ、v4 の作法にも沿う。`tailwind.config.ts` は移行後に削除候補。
